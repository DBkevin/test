# 抖音本地采集异常轨迹分析（2026-03-17）

## 本次用户确认的错误轨迹

用户复盘的真实轨迹是：

1. 本地采集待命后，手动冷启动抖音。
2. 自动流程正确进入：
   - 首页
   - 团购
   - 搜索输入页
   - 搜索 `郑州美莱`
   - 结果页
   - `郑州美莱医疗美容医院` 店铺首页
3. 第一次进入店铺首页后，脚本发生了向下滚动。
4. 随后脚本不再停留在目标店铺首页团购区域，而是进入了错误页面链路：
   - 点到页面底部频道/入口区
   - 进入了“医疗美容”频道页
   - 在频道页又点进了别的店铺
   - 在第二个店铺页又点了头部搜索
   - 又重新输入关键词、重新搜店、重新进店
   - 然后再次下滑

这不是单纯的“误点一次”，而是一次页面状态识别失败后，整套首页搜索脚本在错误页面上被重放。

## 当前最可能的根因

### 根因 1：首屏还没稳定抓取，就提前进入了向下滚动

当前 `CaptureCoordinator.collectDetailRecords()` 的预期是：

1. 先抓当前视口
2. 再决定是否滚动

但从这次日志看，只看到了：

- 进店成功
- 向下滚动

没有看到一条明确的“首屏已经抓到记录”的证据。

因此当前最大的怀疑是：

- 首次进店后，`scrapeCurrentPageNow()` 可能因为 `rootInActiveWindow` 尚未稳定、或插件识别未命中，导致首屏抓取实际上没有成功。
- 但采集循环并没有把这个状态当成“先继续原地等/重试”，而是直接进入了第一次下滑。

### 根因 2：进入店铺尾部后，页面识别把“当前仍在目标店铺页”判断丢了

`cold_start_26s.png` / `cold_start_final.xml` 对应的页面，并不是“猜你喜欢”或“推荐频道页”，而仍然是目标店铺体系内的尾部页面，具有这些信号：

- 顶部仍有 `收藏`
- 页面中仍有团购卡
- 有 `展开更多`
- 有 `预约到店专属礼`
- 有 `用户评价`
- 底部固定栏仍存在

也就是说：

这仍应被视为“目标店铺页的可恢复状态”，而不是“已经离开目标店铺”。

一旦这层识别失败，后面的恢复逻辑就会误以为：

- 当前不在店铺页
- 当前也不在结果页
- 应该重新走 `团购 -> 搜索 -> 搜店 -> 进店`

而这时如果脚本已经处于一个错误页面上下文，首页坐标就会落在完全不同的元素上，最终出现用户描述的“频道页 -> 别的店铺 -> 搜索 -> 再进店”的连锁误操作。

### 根因 3：坐标脚本缺少“页面前置断言”

当前抖音自动路径里仍然存在固定点位步骤，例如：

- 首页 `团购`
- 团购页搜索入口
- 搜索页提交
- 结果页店铺入口带

这些点位只有在“当前页面确实是预期页面”时才安全。

当前问题暴露出：

- 当状态识别失败时，坐标动作仍然会被执行。
- 一旦在错误页面上重放这些点位，就会进入错误业务链路。

所以后续不能只靠“尽量识别正确”，还必须加：

- 页面前置断言失败时，禁止执行坐标动作。

## 这条链路应该怎么改

### 1. 首次进店后，不允许在“零记录、零确认”状态下直接下滑

应该改成：

1. 进入店铺首页
2. 明确确认首页锚点
3. 原地抓取当前视口若干次
4. 至少满足以下之一，才允许第一次向下滚动：
   - 已经抓到记录
   - 已明确识别到当前页是目标团购页，但当前屏没有新增记录

否则就继续原地等待/重试，不下滑。

### 2. “店铺尾部页”必须继续认作目标店铺页

以下组合应当被视为目标店铺页或目标店铺尾部页：

- 顶部 `收藏/关注`
- 当前屏仍有团购卡
- `展开更多/收起`
- `预约到店专属礼/预约到店送好礼`
- `用户评价`
- 底部固定栏存在

只要还满足这类组合，就不应该重新启动首页搜索流。

### 3. 所有坐标动作前都要加页面断言

例如：

- 点首页 `团购` 前，必须断言当前是抖音首页 feed。
- 点团购页搜索框前，必须断言当前是团购页。
- 点结果页商家入口带前，必须断言当前是商家结果页。

如果断言失败，应该：

- 先停
- 再恢复页面
- 或者直接中止本轮采集

绝不能在未知页面上继续重放首页坐标。

### 4. 服务重连后的恢复逻辑要优先恢复“当前店铺态”

服务重连后应该按优先级判断：

1. 是否仍在目标店铺首页
2. 是否仍在目标店铺尾部页
3. 是否仍在目标商家结果页
4. 只有以上都不是，才回到首页搜索流

## 明天优先要做的代码点

优先级从高到低：

1. `CaptureCoordinator`
   - 首次进店后的首轮采集，改成“原地重试优先”，不再首屏失败就直接下滑。
2. `SearchController.isOnMerchantDetailPage()`
   - 放宽到能识别“店铺尾部页”。
3. `SearchController`
   - 为所有坐标动作补页面前置断言。
4. `FrameworkAccessibilityService`
   - 保留/补足 `force scrape` 失败原因日志，避免下轮继续靠猜。

## 当前判断

今晚最重要的结论不是“某个坐标又点错了”，而是：

当前脚本的真正风险在于：

- 首屏未稳定就下滑
- 尾部页识别丢失
- 丢失后在错误页面重放首页坐标

这三个问题叠加，才形成了用户看到的整条异常轨迹。
